# Training log and coach view: preserve first, extend after scenarios

**Date:** 2026-09-05. **Status:** source audit and proposed follow-up; no new coach implementation, database writes or production verification.

The existing training log, development report, coach ratings and notes, roster analytics, team training and homework features are still in the app. The current scenario work should connect to these features, not replace them. The owner’s sequence is explicit: finish the scenarios, then improve the coach view.

This audit inspected current local code and checked-in SQL. It establishes implementation and data contracts, not that every migration is applied or that cloud permissions work in production. The full-app sample at `?demo=player` is useful for demonstrating the experience; sample records are not proof of live synchronization or measured development.

## Storage and sample boundaries

- [trainingLog.js](../../src/utils/trainingLog.js) keeps `rinkreads_training_log` in local storage, partitioned by player ID, with at most 200 sessions per player. A save writes locally and starts a separate cloud insert for non-ephemeral IDs. Local storage errors are swallowed by [storage.js](../../src/utils/storage.js); the UI can show a saved response without durable storage confirmation.
- The cloud write is an **insert**, despite a comment calling it an upsert. There is no stable session ID/idempotency key, pending queue, retry, acknowledgment status or player-side pull/merge in the inspected flow. Supabase’s returned error is not checked by the insert helper. Local success therefore does not establish that a coach received the entry.
- [migration_0007](../../supabase/migration_0007_training_sessions.sql) declares the training table, player-owned CRUD and coach-read access through the team owner. This is repository intent. [migration_0022](../../supabase/migration_0022_rls_privilege_hardening.sql), around line 249, records that `training_sessions` was absent in a live check on **2026-08-02**. That historical observation is not a fresh production check; current availability needs read-only verification before claiming cloud reliability.
- [previewPlayer.js](../../src/data/previewPlayer.js) includes sample training, prices, notes and coach feedback. App preview initialization writes these into the preview player’s local cache. [devBypass.js](../../src/utils/devBypass.js) identifies canonical demo/preview/dev IDs so normal training saves skip remote writes. The separate coach demo seeds plausible local sessions for its roster.
- The coach demo rating save currently persists the general note locally; it does not persist the whole new rating map through the live path. The demo can demonstrate controls without proving a coach assessment survives a real account round-trip.

## Specific gaps to resolve during the later coach work

1. **Verify and enforce the private-note boundary before relying on its label.** `saveCoachPlayerNote` stores `__general_notes__` in `coach_ratings`. [schema.sql](../../supabase/schema.sql), lines 212–225, permits a player to select their own coach-rating rows without excluding that sentinel. `getCoachRatingsForPlayer` also does not exclude it. Thus the UI’s “only you” claim is unsupported by the checked-in policy. This is a source-policy mismatch, not a claim that a production leak was tested. Use a genuinely coach-private store/policy, test player and unrelated-coach denial, and distinguish shareable feedback from private working notes.
2. **Make training persistence reconcilable.** Add stable entry identity, explicit local/cloud status, retry and safe deduplication, then restore entries on another authenticated device. Preserve every supported activity, unit, instructor, price and note. Decide edits, deletion and retention explicitly rather than losing history beyond the current cap without review.
3. **Normalize real and demo roster data.** CoachHome attaches fetched history as `quiz_history`, while `RosterRow` reads only `quizHistory`; team analytics already accepts both. The roster’s local “total minutes” sums all values without checking unit, so puck counts can be counted as minutes. Fix the data adapter and keep durations, puck counts and quiz sessions separate before redesigning the display.
4. **Establish real coach attribution and membership.** Preserve each coach’s ratings and notes separately instead of flattening skill IDs. Define owner/assistant access through stored membership, not display labels. Add assessment history only with explicit authorship and timestamps; do not infer a trend from overwritten current values.
5. **Provide a real review request and full player view.** After scenarios are stable, let a player deliberately request feedback on a specific attempt. A coach view should show the exact play version, read history, named focus role, chosen positions/actions, pacing/feedback mode and optional reason, alongside existing training and ratings. Add open/responded status and player-visible replies. Keep internal rubrics, source evidence and private coach reasoning out of child UI.
6. **Connect assignments to completed work without fabricating completion.** Retain free-text homework, but add optional reviewed scenario-family/version links and separate manual completion from validated attempt completion. Repeated attempts and alternative defensible answers must remain visible rather than collapsing into a single unexplained percentage.

## Agreed sequencing for follow-up

1. Finish consistent 3D scenarios, reliable answer interactions, causal multi-read state and age-appropriate wording. Preserve the existing training/report routes throughout.
2. Before opening a broader coach release, verify real table availability and access policies; repair the identified privacy and synchronization contracts. Use test accounts and an explicit approved verification plan, not real child records for experimentation.
3. Build the coach player view around existing ratings, training, quiz trends and homework, with exact scenario replay and clear attribution. Add the feedback-request inbox and private/shared note separation.
4. Verify player entry → save/reload → second-device retrieval → permitted coach view → feedback reply → player report, including offline failure, denied access and demo isolation. Cosmetic demo success alone is insufficient.

**Audit outcome:** retain the existing feature set. The scenario improvements are the first phase; a stronger coach view is the next phase, with the above gaps recorded rather than disguised by sample data.
